### FlorLogic:
**FlorLogic** es un aplicativo de captura en campo para empresas productoras agrícolas con énfasis en flores, con reportes actualizados sobre inventario y estado. 
|Problema|Cifra que representa|
|---|---|
|El operario de campo llena formas a lápiz|2-4 horas al día|
|Un encargado rotativo digita|4-6 horas semanales|
|El dato sobre lo que se vende llega tarde| 8 días|
|Pérdidas porcentuales| 6-10%|

 > ## **¿Qué hace que el sistema ya no sea útil?*****:*** 
 >### **"Que los datos no sean correctos"**

**Dejando la confiabilidad como prioridad principal:** La principal prioridad será asegurar que los números cuadran para trabajar con ellos.

La idea que guía el despliegue es que la finca opere sola, es decir, todo lo necesario para capturar, guardar y consultar vive en la red local, y la nube solo acompaña.

>| Nodo | Qué corre ahí |
>|---|---|
>| **N1 · Dispositivo Android** | La aplicación de captura y su almacén local cifrado. Son 3 unidades que pone la empresa; trabajan en el invernadero sin conectividad y sincronizan al volver a la red local de la oficina. |
>| **N2 · Servidor de la finca** | El API Gateway, el backend de la finca, la caché de producciones activas y la base de datos. Hay uno por empresa, opera sin internet y es el producto que se compra. |
>| **N3 · Computador de oficina** | La aplicación web del sistema, que se ejecuta en el navegador y no guarda estado propio. La usan unas 12 personas, más unas 20 que solo consultan. |
>| **N4 · Infraestructura en la nube** | Los servicios en línea y la custodia de respaldos: reciben los respaldos ya cifrados con la llave del cliente, sin poder leerlos, y entregan las versiones nuevas del sistema. Nunca están en el camino crítico de la finca. |

# 9. Forma de desarrollo
Para el desarrollo completo mediante agentes se utilizó un cúmulo de diferentes cosas mencionadas previamente en diferentes segmentos **Skills, Spec-Driven-Design** entre otros, estos son procesos integrados con agentes para lograr un resultado más determinista en modelos de alta temperatura. Utilizando diferentes *_kits_* se logra un flujo de trabajo que considera completamente el concepto **human in the loop.**
El flujo de trabajo comienza desde la especificación de los procesos, mediante herramientas de desarrollo constante propias y públicas se define el comportamiento esperado del código mediante preguntas determinadas por herramientas que guían al agente a mantener un flujo de trabajo continuo y totalmente predecible, en las herramientas para especificar se encuentran diferentes plantillas de trabajo, que combinan flujos de trabajo recomendados desde el mismo agente Opus 5.5 y flujos de trabajo personalizados que cumplen requisitos impuestos por el humano, una plantilla se compone, de referencias directas de consulta para el proceso **MCP** de librerías locales que cuentan con libros de diseño desarrollo y bibliografía del curso, del mismo modo cuenta con información cruda de sitios de acceso público como **Refactoring Guru** que se utilizó como documentación de referencia **para implementar patrones de diseño** dentro de código de diferentes lenguajes, cada vez que se determina un proceso dentro de la especificación se hace **referencia tanto a los libros de donde surgen estos conceptos necesarios para el correcto funcionamiento, también al código crudo que vive en las bibliotecas locales que se utiliza como ejemplo en rondas de verificación humana posterior**. Una vez detallado un flujo de trabajo, **contexto determinado o plantilla seleccionada**, se procede a generar código de manera sucesiva y controlada con **límites especificados** dentro de la skill de la sesión, este código es mostrado y para confirmar una **verificación** el humano debe ser interrogado por el agente mediante **preguntas, pruebas, implementaciones crudas, con o sin ayuda para verificar el entendimiento del humano**, este último proceso se aborda más como el proyecto de aprendizaje personal de los desarrolladores, por lo cual es cambiante, pero se hace el intento completo de verificar la información que se va recibiendo, una vez este código se da por listo, **se generan pruebas desde la documentación de pirámide de pruebas** y documentación oficial de las tecnologías seleccionadas, se  propende a utilizar un workflow automatizado para conseguir los límites de tiempo del proyecto, mediante se fomenta un aprendizaje agéntico independiente completo.

# 10. Estrategia de ramas

Este repositorio usa las siguientes ramas:

- `main` — rama principal, contiene el código y la documentación estables/listos para producción.
- `documentacion-desarrollo` — documentación en curso, borradores y contenido en preparación.
- `documentacion-lista` — documentación revisada y lista para integrarse a `main`.
- `codigo-desarrollo` — desarrollo activo de nuevas funcionalidades.
- `codigo-testing` — código en pruebas/QA antes de pasar a producción.
- `codigo-listo` — código validado y listo para integrarse a `main`.

Flujo sugerido: el trabajo nuevo se hace en `codigo-desarrollo` o `documentacion-desarrollo`, pasa por `codigo-testing` (o revisión, en el caso de documentación) y de ahí a `codigo-listo` / `documentacion-lista`, para finalmente integrarse a `main`.

Ver [docs/README.md](docs/README.md) para la estructura de la documentación.
